# B站直接发现

数据源页的「B站抽奖发现 → 更新话题」直接读取 B站话题动态，不依赖薯片等第三方数据库。

默认话题 11 个，全部定义在 `src/lottery_discovery.py` 的 `TOPICS`：1040028（bilibili互动抽奖）、1140180（抽奖专用频道）、1091435（互动抽奖合集）、60094（转发抽奖合集）、11592（抽奖互动）、1051197（BiliBili动态抽奖）、1261901（抽奖！！！）、1267572（互动抽奖活动）、1028370（互动抽奖好运来）、1013444（动态抽奖#）、1055656（转发动态抽奖！）。这是话题覆盖范围，不是全站抽奖全集；没有带入这些话题的活动仍需通过 UP 合集或监控发现。

使用 `app.bilibili.com/x/topic/web/details/cards`，`sort_by=3`（最新），每页 20 条，沿接口 offset 分页。首次分批补齐最近 7 天的可见内容；每次先检查最新页，再各读取最多一页待续更新和历史页，每个话题最多 3 页。按钮可重复点击，任务可取消；完成页在本地记录进度，失败页不推进游标。历史完成之后继续增量更新。

转发动态先还原到原活动，按原动态发布时间排序；同一页、跨话题和既有活动库分别去重。复用现有分类：平台开奖接口识别官方互动抽奖、预约卡片加开奖接口识别预约抽奖、正文模型识别非官方转发抽奖；充电和非抽奖活动不入库。无需执行任何关注、评论或转发来采集。

「补齐近7天」先检查话题最新页，再沿已保存的历史位置持续读取，直到整页动态早于最近 7 天，或接口返回没有下一页；保留原有限速，每页处理完成后立即保存位置。可取消，失败或取消后再次点击即可续采，不必每补一页手动启动一轮。普通更新仍使用上述有限页数预算。分页游标重复时停止并保留进度。

界面显示已遍历话题数、未完成话题累计扫描条数，以及新版本实际读取到的最早发布日期。3/4 表示三个话题已结束分页，不表示完成了全部活动的 75%。接口不提供历史总页数，因此不显示估算完成时间；完成仅指最近 7 天范围检查完毕，正文待重试数量另行展示。

本地进度位于用户数据 `data/lottery_discovery.json`。接口错误或结构变化会停止并报告，不把失败当作已完成。B站可能调整接口或限制可见历史，源只承诺采集接口实际返回的内容。

单条动态正文重试后仍无法读取时，继续识别并入库其他活动，将该 ID 持久化到 `pending_ids`，不标记为已处理。后续每轮在新动态扫描后最多重试 5 条，仍失败的轮转到队尾；同一轮每个 ID 只处理一次。界面显示「完成 · 待重试 N 条」，日志保留具体 ID。登录、模型服务、话题接口错误及取消仍按原流程报告，不会被当成正文暂不可用吞掉。

研究参考：[LotteryAutoScript](https://github.com/shanmiteko/LotteryAutoScript) 的话题/用户动态发现思路；本实现独立编写，实际接口和分页格式已用只读请求验证。

发布时间以原活动的 module_author.pub_ts 为准；新的转发不会使旧原活动重新入库。发布时间未知则跳过，不拿入库时间当发布时间。旧版本跨年游标会重置到最新页，保留已有活动去重记录。旧待重试队列也受同一时间范围限制。

截止时间未知保留为空，界面显示「未公布」，不再用入库或参加时间加半年制造日期。活动旁的「移出」手动归档，更新不会自动恢复；已归档里可恢复。归档活动从预选池可执行候选中排除，已排队的归档项执行时跳过。

采集窗口为滚动近 7 天，按原动态发布时间过滤，再进入正文识别。升级时重置旧窗口的历史分页位置，保留已处理记录，并移除窗口外或发布时间未知的正文重试项；已有活动库和预选池不受影响。
